How this index is built

I'm Pedro A. A. Silva, a data engineer. I built this index and run it every day: a pipeline that collects job postings from public career boards, turns them into one clean dataset and publishes it here. This page explains what the pipeline does and how it's built. The code is private.

From career boards to this page

  1. CollectCompany career boards (ATS), job platforms, APIs and feeds, read in parallel within each source's rate limits.
  2. Clean & enrichEach source's format becomes one schema: text, salary, location, remote scope, seniority, skills and category.
  3. DeduplicateThe same job posted on several sources counts once.
  4. Track changesEvery run is a snapshot. Each job keeps its history: first seen, updates and closing date.
  5. ModelA lakehouse with bronze, silver and gold layers, modelled in dbt. It runs on DuckDB locally and on Databricks (Delta Lake) in the cloud.
  6. PublishA daily scheduled workflow checks the data and publishes this static site.

A note on infrastructure

I wanted to keep this project simple and avoid spending money on infrastructure.

The pipeline started on free GitHub Actions runners. When the daily run outgrew the free monthly minutes, I moved the workflows to a self-hosted runner on an Oracle Cloud free-tier machine (4 vCPU, 24 GB). State is stored in GitHub release files, the website is published through GitHub Pages, and the lakehouse uses a free Databricks workspace.

One small machine to look after, no paid databases, and no hosting costs.

Instead, I focused my time on what matters most: collecting reliable data, cleaning it, keeping historical records, and checking data quality.

The pipeline already runs on Databricks, so if I need more computing power later, I can scale up without having to redesign everything.

Challenges and how I solved them

Thousands of career boards, each different

Challenge: every ATS and job platform has its own API, format, rate limits and failure modes.

Solution: one small, pluggable collector per source. Each one runs in parallel with its own timeout and worker limit and maps the result to one shared schema.

Finding where companies post their jobs

Challenge: companies embed their job boards on career pages in many different ways.

Solution: discovery tools that inspect career pages and detect the board behind them. A board is only added after its answers are verified, and conflicts go to manual review instead of overwriting data.

The same job, many times

Challenge: one posting shows up on several sources, gets reposted, or comes back from a new source as if it were new.

Solution: a stable identity and a content fingerprint for every job. That separates a really new job from a new source, and a real closing from a gap in one day's run.

Knowing what changed, day by day

Challenge: a list of today's jobs says nothing about which are new, which changed or how long they stay open.

Solution: immutable daily snapshots turned into a full history (SCD Type 2). That gives first-seen and closing dates, plus a Kaplan-Meier estimate of how long jobs stay open that still counts the ones that are open.

Keeping a bad run off the site

Challenge: a source can fail quietly and a run can come back half empty.

Solution: each run is compared with the previous ones: failed or empty sources, volume drops, gaps, slow runs. A run that collapses never replaces the published site, and errors fail the workflow.

Same models, laptop and cloud

Challenge: develop cheaply on a laptop and still run on a real cloud platform.

Solution: one set of dbt models that builds the lakehouse on DuckDB locally and on Databricks (Delta Lake, Auto Loader, incremental MERGE). Both were checked to give identical results.

Big data on a small machine

Challenge: the daily build first ran on a free CI machine with about 7 GB of memory.

Solution: streaming and batching instead of loading everything at once cut peak memory from 5.05 GB to 2.81 GB.

Messy text

Challenge: salaries in many currencies and periods, locations like “Remote (LATAM)”, one skill written ten ways.

Solution: parsers and a taxonomy normalize each field and record how confident they are. Values that can't be read stay unknown instead of being guessed.
