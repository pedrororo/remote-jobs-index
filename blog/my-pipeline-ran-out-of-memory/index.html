My pipeline ran out of memory at 149k jobs. Now it fetches 400k in under 3.5 GB

October 28, 2026 · 4 min read

The Jobs Index is rebuilt every day by a GitHub Actions workflow. The runner it uses has about 7 GB of RAM.

At around 149,000 jobs, the fetch step peaked at 7.2 GB. Then the first run with Brazil's Gupy listings didn't fail with an error. It just stopped:

runner received a shutdown signal

No stack trace, no failing line. The machine ran out of memory, and the operating system ended the job.

Today the same step collects about 400,000 jobs and peaks between 2.8 and 3.3 GB. Here is what changed, in the order I did it.

First, make memory a number

You can't tell whether a fix worked if the only signal is "the run survived this time".

The fetch step now runs under /usr/bin/time -v, and a report step prints the maximum resident set size after every run, even a failed one. Memory became a metric I can compare between runs, like job counts or duration.

I also added 6 GB of swap to the runner. That is a safety margin, not a fix: with swap, a run that goes over the limit gets slower instead of being killed. The goal is still to stay below 7 GB without it.

Store a fingerprint, not the data

The lifecycle tracker (the part that decides when a posting has closed) needs to notice when a job's description changes. To do that, it kept every description it had seen.

But it never read those texts. It only compared them. A sha256 fingerprint of each description answers the same question in a few dozen bytes.

That change took the lifecycle state from 1.3 GB to 245 MB (48 MB compressed). The peak fell to 6.15 GB.

Drop raw data as soon as it's used

Many career boards return job descriptions as HTML. The pipeline converts them to plain text and never needs the HTML again, but it was keeping both copies until the end of the run.

Dropping the HTML right after conversion saved about 1.5 GB.

I couldn't measure that run cleanly, though. The enrichment cache key includes a hash of the code that does the enrichment, so my change to the description code made the next run recompute every job. That run was slower and used more memory for reasons unrelated to the fix. A measurement is only useful if the rest of the run stays the same.

Trimming was not enough

Those fixes bought headroom, but they didn't change the shape of the problem. Every job, with its description, was still in memory at once, along with the copies made by history, enrichment and the exports. Peak memory grew in a straight line with the number of jobs.

That is a bad property for a project whose goal is to keep adding sources. Each new company would bring the next shutdown closer.

Stream, don't collect

The fix that changed the shape was to stop holding the whole dataset in memory.

  • As each fetcher (or each company board) returns its jobs, the pipeline does all the per-job work right away: the raw snapshot, dropping the HTML, recovering missing company names, the lifecycle observation and the publication filters.
  • Jobs that will be published go to a spool on disk. Only small per-job records stay in memory.
  • The export reads the spool back in batches, newest first, so only one batch of full, enriched jobs is in memory at a time.

New fetchers accept a callback that hands jobs over as they arrive, so they stream too.

The two local tests were run on my machine, not on the runner, so compare them with each other rather than with the runner rows.

The peak is not perfectly flat. It moves with batch contents and with how much work a run has to redo. But it no longer grows with the number of jobs: going from about 230,000 to 400,000 jobs did not move it much.

The cost moved somewhere else

Streaming didn't make the problem disappear. It moved it.

  • To disk. A spool, swap and a large export all live on the runner's disk. On October 23 they filled it, so the workflow now removes toolchains this job never uses before it starts.
  • To time. Memory is no longer what limits adding sources; runtime is. When I added 86 large employers on Workday, the first run took 2 hours and 11 minutes to fetch, compared with 35 minutes before, because nothing was cached yet. The next run, with the cache warm, took about 1.5 hours. A time budget for Workday and a step timeout keep a slow run from overrunning the job.

I prefer these constraints. A slow run still finishes and publishes. A killed run only leaves a "shutdown signal" in the log.

What I'd do first next time

Measure before fixing. Then look for data you keep only to compare, and data you keep after you've used it. Those fixes are cheap.

But if memory grows in a straight line with your data, trimming only delays the limit. In a pipeline meant to grow, the change that lasts is the one that makes memory independent of dataset size.
