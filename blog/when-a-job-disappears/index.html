When a job disappears: did it close, or did my pipeline fail?

October 26, 2026 · 4 min read

Yesterday, a job appeared in my index. Today, it is gone.

Did the company stop hiring? Did the source stop returning it? Or did something break in my pipeline?

All three can produce the same result: a missing record. But they tell very different stories to someone searching for work, or reading a chart about the job market.

While building the Jobs Index, I had to decide what evidence was enough to mark a posting as closed. Comparing yesterday's records with today's was only the starting point.

Missing is an observation. Closed is an inference.

A daily collection tells me which postings my pipeline observed at a particular time. It does not give me a complete account of what happened at each employer.

A posting might disappear because:

  • The employer removed it from its career board.
  • A request failed or returned an incomplete response.
  • A parser stopped recognizing part of the response.
  • An older posting fell out of a feed that only includes recent items.
  • I changed which sources the pipeline collects.

If I turn every disappearance into a closure, a collection problem can become an apparent drop in hiring.

So the lifecycle tracker keeps an intermediate state: POSSIBLY_CLOSED.

First, check whether absence is meaningful

Before counting a missing observation against a job, my tracker checks two things:

  1. Did the job's collector report a successful run?
  2. Did that same collector return at least one posting for the same company?

If either answer is no, the tracker preserves the job's previous state. That run does not add a miss.

The second check matters because one collector can cover many companies. Getting results from company A does not prove that company B's board was collected correctly.

This is a conservative rule with a tradeoff: if a company removes its very last posting, there are no remaining jobs to confirm that company's coverage. The tracker may preserve an old status rather than infer a closure from silence.

Even when both checks pass, a partial response can still hide a job. These checks make an absence more useful as evidence; they do not make it certain.

Three misses need a clock

By default, my pipeline requires at least three qualifying misses and 36 hours since the first miss before marking a job as CLOSED.

Why both?

Counting runs alone lets three manual reruns turn a few hours of absence into a closure. Elapsed time prevents those reruns from compressing the waiting period.

Here is an illustrative timeline, assuming each collection passes the checks above:

ObservationWhat the pipeline seesLifecycle state
Monday, 08:00Posting presentOPEN
Tuesday, 08:00First missPOSSIBLY_CLOSED
Tuesday, 10:00Second missPOSSIBLY_CLOSED
Tuesday, 12:00Third miss, only four hours elapsedPOSSIBLY_CLOSED
Wednesday, 08:00Fourth miss, 24 hours elapsedPOSSIBLY_CLOSED
Thursday, 08:00Still missing, 48 hours elapsedCLOSED

If the posting returns before closure, its state goes back to OPEN, the miss counter resets, and the tracker records JOB_RETURNED. If it returns after closure, it records JOB_REOPENED.

Keeping those events means I can reconstruct what the pipeline observed over time, including when an earlier inference changed.

A successful request can still produce bad data

Lifecycle rules handle individual postings. I also need checks on the collection as a whole.

The pipeline compares source and total job counts with the median of the previous seven runs. It flags failed sources, unexpected empty results, and large volume drops.

If the total collection falls below half that recent median, the normal publishing workflow skips replacing the public site. The previous version stays online.

There are limits: source alerts alone do not block publishing, and publishing can proceed if the quality-check step itself fails. The gate protects against a detected collapse in total collection volume; it does not guarantee a complete dataset.

The source changes what disappearance means

A company career board and an RSS feed can both return job postings, but their absences mean different things.

A career board generally aims to list current openings. Repeated absence there is useful evidence that a posting was removed. An RSS feed may only contain the newest entries, so a job can disappear while applications remain open.

That distinction matters when interpreting lifecycle charts. A feed's retention window can look like a very short hiring cycle if I treat every disappearance as an employer decision.

And even a posting removed from a career board does not tell me whether someone was hired. The employer might have paused the search, withdrawn the role, or replaced the listing.

In this project, CLOSED is a lifecycle classification based on observations. It is not confirmation of a hire or the exact moment applications ended.

What I want readers to be able to trust

My previous article looked at the share of collected jobs labeled fully remote. Questions about openings and closures require another layer of care: knowing whether a change came from employers or from my own collection process.

Building that distinction into the pipeline has meant tracking source health, preserving history, allowing uncertain states, and defining what each metric can actually support.

When a number changes, I want to be able to explain the evidence behind it.

How do you handle missing records in a recurring pipeline? What evidence do you require before treating an absence as a deletion?
